# EG13 M5 (Part FX) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give each part a Part FX slot after Σ voices (Off, **Granular** from Clouds, **Granular Delay** from Beads, **Resonator** from Rings, **Reverb** from Elements' reverb) with the Part FX input selector (Part mix / Input / Part mix + Input), host parameters (type, P1–P16, input selector), matrix routing into Part FX P's, a **Live / Studio latency** setting for every rate converter in the synth, state schema 6, EG13 FX's init Granular, and latency, CPU and memory reports in both latency modes.

**Architecture:** Every `NativeRateWrapper` takes a `ConverterQuality`: *Studio* keeps today's converters, *Live* uses the lowest-latency r8brain configuration that meets stated quality floors (chosen by measurement in Task 2). The mode is a per-instance, non-automatable setting applied at the next activate; each mode has its own constant latency. Part FX engines are `VoiceEngine`s like every other slot's, each in its own `NativeRateWrapper` at the module's native rate, held by one `ProcessorSlot` per part (preallocated, padded to one slot latency, crossfaded on a type change). A new `PartFx` class in `core/part/` owns that slot, picks its input by the selector, delays the Input and the bypassing voices so everything stays aligned, and replays per-tick controls (P's after modulation, the part's note, note triggers) delayed by the voices' latency so they act on the sound they belong to. `Part` runs it between the voice mix and level / pan / Mono. Routes into Part FX P's are part-level destinations, evaluated once per 16-sample tick like Part Level. The Synth stashes Part FX settings per engine exactly like the other slots.

**Tech Stack:** C++17, CMake + Ninja, Catch2 v3, r8brain-free-src 7.6, upstream pichenettes/eurorack at f4cfa76 (Clouds, Beads, Rings, Elements + stmlib, unmodified), nlohmann/json, CLAP 1.2.10, clap-wrapper v0.16.0.

**Spec:** `docs/superpowers/specs/2026-10-20-eg13-design.md` (M5 row of §11; §2 diagram; §2.3 Part FX input selector and Input source; §3.1–3.3; §4 Part FX rows; §5.3 part settings; §6 Rate and the EG13 FX init patch; §7.1 "Part FX: type, P1–P8"; §7.2; §9; §10).

## Planning measurements (2026-10-23, this machine, -O3)

- **Wrapper input-path latency** for a 2-in / 2-out engine (r8brain 7.6, `kTransitionBandPercent` 30): 32 kHz engines 472 / 539 / 1077 host samples at 44.1 / 48 / 96 kHz (10.7 / 11.2 / 11.2 ms); Beads Dirty tape (24 kHz) 445 / 444 / 932; Beads Vintage digital (32 kHz) 406 / 467 / 933; 48 kHz engines 232 / 0 / 468. The Part FX slot latency is therefore Granular's, ≈ 539 samples at 48 kHz.
- **One converter round trip, host 48 kHz → 32 kHz → 48 kHz, transition band 30 %** (owner's measurement, 2026-10-23): linear 206 dB 430 samples (8.95 ms); linear 120 dB 208 (4.32 ms); linear 96 dB 217 (4.52 ms); minimum phase 206 dB 366 (7.62 ms); minimum phase 120 dB 169 (3.52 ms). Not monotonic: r8brain picks different stage structures, so Task 2 measures every candidate rather than extrapolating.
- **CPU per instance, bare module at native rate:** Clouds 0.23–1.06 % of a core (Spectral, 16-bit, worst), Beads 0.30–1.30 % (Digital, Size 100 %, worst). `sizeof(clouds::GranularProcessor)` 9096 B, `sizeof(beads::Processor)` 25824 B.

## Owner decisions (2026-10-23)

Taken on the first draft of this plan; Task 1 records them in the spec and the manual.

1. **Part FX has P1–P16** (spec §7.1 said P1–P8): Granular needs 13 controls (VCV `Clouds.cpp:6-21`: nine knobs, In Gain, Freeze, Mode, Quality), Granular Delay 15 (`beads.cc:183-236`: eight knobs, four randomisation attenuverters, Freeze, Quality, Seed). The IDs and M4's code space (64..79) already have room.
2. **Part FX input selector:** *Part mix* (Σ voices into the FX), *Input* (the part's Input, as its Input source routes it, into the FX; the voices bypass the FX, delayed by the slot latency, and are still heard, aligned), *Part mix + Input*. With Part FX Off the selector is ignored and the part mix passes, so Off never leaks the Input.
3. **Latency:** about 22 ms is unacceptable for live playing. A **Live / Studio** latency setting: Studio keeps today's full-fidelity converters; Live uses low-latency converters for playing and tracking. Widening the transition band is not acceptable. Every converter in the synth (Sources, Shaper, Part FX) follows the setting.
4. **Execution** is subagent-driven.

## Provisional rulings (flag for owner)

Each line: what was chosen — why — what it costs to change.

1. **Live converter floors and selection** (owner's provisional floors): a candidate qualifies when, at every host rate (44.1, 48, 96 kHz) and every converted native rate in the synth (24, 32, 47.87234 (Plaits), 48 and 96 kHz; the mod engines are sampled, not converted), (a) **stop-band rejection ≥ 96 dB**: on the input path, a sine anywhere from the native Nyquist to the host Nyquist leaves at most −96 dB (aliased) relative to the same sine at 1 kHz; on the output path, every image above the native Nyquist of a sine anywhere in the passband is at most −96 dB; and (b) **passband ripple ≤ 0.1 dB**: the round-trip magnitude stays within ±0.1 dB of its 1 kHz value from 20 Hz to f_pass, where f_pass is the frequency at which the Studio round trip at the same rates first falls 0.1 dB below its 1 kHz value (so Live is never duller than Studio). Rule: among qualifying candidates, the lowest worst-case wrapper input-path latency at a 48 kHz host across the native rates; ties go to linear phase, then to the higher attenuation — the owner's floors, made measurable — the floors are two constants in the test.
2. **Live candidates:** r8brain `CDSPResampler` with ReqAtten ∈ {96, 108, 120, 136, 150, 180.15} dB × phase ∈ {linear, minimum}, transition band 30 % throughout; plus, for each, the input prime reduced from `2 × nativeBlock` to `1 × nativeBlock` (+ withheld + 1), kept only if `inputUnderruns()` and `inputOverruns()` stay 0 at every host rate with host blocks of 1, 7, 129 and maxBlock samples — the owner's list, plus the one wrapper margin that is not a converter — anything else (a different converter library) is a new task.
3. **Minimum phase is allowed only if onset alignment holds:** an impulse's peak lands at the reported latency ± 1 sample on every path, and Dry plus a unity engine path sums without a comb notch deeper than 1 dB below f_pass — minimum phase smears group delay, which Dry and engine dry/wet mixes would expose — dropping minimum phase from the candidates is one line.
4. **The setting is a stepped master host parameter** `MasterParam::LatencyMode = 6` (0 Live, 1 Studio; append-only), registered without `CLAP_PARAM_IS_AUTOMATABLE`, so hosts can show and save it before M6's UI exists but not automate it; it is saved in state with the other parameters — spec §7.1's precedent of exposing settings as stepped host parameters before the UI — a state-only key would need the UI to change it.
5. **Defaults:** the instrument starts in Live, EG13 FX in Studio (owner's provisional ruling) — the instrument is played live; the FX is usually mixed — a default.
6. **Applying a change:** the Synth keeps running in the mode it was prepared with; a different value (from the host, or a state load) makes the plugin call `host->request_restart()` from the main thread, and the next activate prepares in the new mode and reports its latency with `latency->changed()` (CLAP rules). VST3 maps this to `restartComponent(kLatencyChanged)` (`clap-wrapper/src/wrapasvst3.cpp:1333-1339,1352`). **AU:** clap-wrapper v0.16.0's `restartPlugin()` is empty (`src/detail/auv2/auv2_base_classes.h:584-586`), so in an AU host the change applies when the host next initialises the plugin (reopening the project or changing the sample rate); `latency_changed()` then posts `kAudioUnitProperty_Latency` (`src/wrapasauv2.cpp:1054-1056`). Documented in the manual — fixing it needs a clap-wrapper change (owner question).
7. **Spec §3.1 wording: Part FX engines are `VoiceEngine`s that receive notes.** They reuse `NativeRateWrapper`, `ProcessorSlot`, padding and crossfades; `noteOn` carries the part's note triggers and `setNote` its pitch — the spec's "no notes" cannot hold for a Resonator whose pitch follows notes — a separate interface would need its own wrapper. Task 1 amends §3.1, flagged for the owner.
8. **P layout and one host default per P position** (CLAP has one default per parameter, M3 ruling I1): P1–P4 0.5, P5 0.75, P6 0.5, P7–P12 0, P13–P16 0.5; every engine's own defaults equal these, so a host reset never changes a Part FX from its defaults. P1 is the Mix of every engine, so "Part FX P1" always means dry/wet. — the shared value per position — moving a control later re-means saved projects (fine before release).
   - Granular: P1 Blend, P2 Position, P3 Size, P4 Pitch, P5 Density, P6 Texture, P7 Feedback, P8 Reverb, P9 Freeze, P10 Mode, P11 Quality, P12 Spread, P13 In Gain.
   - Granular Delay: P1 Dry/Wet, P2 Time, P3 Size, P4 Pitch, P5 Density, P6 Shape, P7 Feedback, P8 Reverb, P9 Freeze, P10 Quality, P11 Seed, P12 unused, P13 Time Random, P14 Size Random, P15 Shape Random, P16 Pitch Random.
   - Resonator: P1 Mix, P2 Structure, P3 Brightness, P4 Damping, P5 Spread, P6 Position, P10 Model, P11 Polyphony, P13 Tune; others unused.
   - Reverb: P1 Amount, P2 Time, P3 Diffusion, P4 Brightness, P9 Freeze; others unused.
9. **Density defaults to 75 %** on Granular and Granular Delay, not VCV's 50 %: both modules make no grains between about 47 % and 53 % (`clouds/dsp/granular_processor.cc:97-102`, `beads/dsp/trigger_generator.cc:265-280`), so the EG13 FX init patch would only blend dry — one default.
10. **Wet/dry:** Granular and Granular Delay use their own dry/wet (the module's dry path, including Beads' bit-reduced dry and Clouds' 16 kHz band limit at 32 kHz); Resonator gets an EG13 Mix (linear dry/wet inside the adapter at its native rate); Reverb's Amount is Elements' own crossfade — keeps each module's character and bit-exact fidelity — a host-rate dry path in `PartFx` is the alternative.
11. **Granular In Gain:** P13 maps to gain 2 × P (50 % = unity: EG13 ±1.0 reaches Clouds' int16 full scale, as VCV's ±5 V does at gain 1.0); the input is clamped to int16 as VCV does (`Clouds.cpp:120-121,151-152`) — EG13's default level passes unchanged — a mapping constant.
12. **Granular Pitch:** P4 is ±24 semitones (VCV ±2 V × 12, `Clouds.cpp:72,167`); it does not track notes (a route from Note can) — the hardware's V/OCT is a jack — a tracking switch could be appended.
13. **Triggers from notes:** every note-on the part plays (a voice trigger, not a legato glide; on an Always-on part, every key press) sends one trigger to the Part FX: Granular's TRIG (sets `trigger` and `gate` for one block, `Clouds.cpp:133-135,162-163`), Granular Delay's SEED gate when Seed = Notes (a 1 ms gate), the Resonator's strum — notes are the only gate source a part has — a route-driven trigger is a later addition.
14. **Granular Delay Seed:** *Free* (SEED unpatched: Density alone makes grains) / *Notes* (note-ons patched into SEED: below 48 % Density divides the note clock, above 52 % it is the probability, in between every note is a grain, `trigger_generator.cc:132-137,255-290`); the seed button and the firmware's 2.5 ms seed delay (`beads.cc:141-148`) are not used — default Free keeps the module's normal behaviour — a list append.
15. **Granular Delay runs at its Quality's codec rate** (24 / 32 / 48 kHz): one `beads::Processor` (one set of buffers, as the hardware shares them across qualities) is driven through three inner wrappers, one per rate, padded to the slowest; a Quality change fades out over 10 ms, calls `Configure`, restarts the new rate's conversion and fades in over 10 ms (the hardware mutes 250 ms, `beads.cc:292`) — running all qualities at 48 kHz would halve Dirty tape's times — removing the nested wrappers is local to `BeadsEngine`.
16. **Granular Delay input stage and scope:** no automatic gain control (EG13's gain staging sets levels); input at unity, clamped to ±1 as the manual-gain path does; Dirty tape adds the manual path's soft clipping at amount 1 (`beads/gain_control.cc:149-166`); stereo always (`Configure(media, false)`, no mono buffer mode); the wavetable synth mode, assignable CV and output gate are left out — the parts of the firmware a part's insert needs — each is an append.
17. **Resonator as Part FX:** one Rings instance per part, the part mix as its exciter (internal exciter off), Polyphony 1 / 2 / 4 (default 1, as the module), strum on every part note-on with that note (the hardware with V/OCT patched strums only on a changed note, `rings/dsp/strummer.h:65-70`), velocity ignored (1.0) — playable in both trigger modes — a branch in `RingsFxEngine`.
18. **Resonator pitch:** the note of the part's most recently started voice + transpose + the part's pitch bend + Tune (±12 st); before any note, the Base note; **on an Always-on part, the held key, and the Base note when no key is held** (as its voice does) — spec §4 says "Base note when Always on"; this follows spec §5.3, where notes change an Always-on part's pitch — one function in `Part`.
19. **Reverb mappings:** Amount → `set_amount(P)`; Time → `set_time(0.35 + 0.63 P)` (the range Clouds gives the same topology, `granular_processor.cc:270`); Diffusion → `0.55 + 0.15 P` (`elements/dsp/part.cc:99`); Brightness → `set_lp(0.6 + 0.37 P)` (`granular_processor.cc:272`); input gain 0.2; Freeze → time 1.0, input gain 0, lp 1.0 (`elements/dsp/part.cc:240-244`) — Elements' Space knob packs these into one control — constants.
20. **Alignment:** Input entering the Part FX is delayed by the voices' latency, so FX(Input) leaves the part at the reported latency, exactly with Dry, in both plugins and both modes; Part FX P's (host and routed), the part's note and the triggers act after the voices' latency, on the 16-sample grid — the M4 rule that each control lines up with the audio it acts on — an event ring would give sample-exact triggers.
21. **Part FX latency within a mode:** every Part FX engine, Off included, is padded to the slowest in that mode (Granular's 32 kHz path). Studio: ≈ 539 samples at 48 kHz (instrument ≈ 22 ms, EG13 FX ≈ 28 ms in total). Live: measured in Task 2 and Task 14; the owner's round trips suggest roughly 40–50 % of Studio's converter latency — spec §3.2's constant-latency rule, per mode — a per-mode table in `latency.md`.
22. **Type change:** the old engine keeps running for the slot latency, then a 10 ms crossfade (`kSlotFadeSeconds`) to the new engine, which starts empty; the old engine's tail is cut — the Filter/Shaper rule, and spill-over would run two engines — a longer fade is a constant.
23. **Part FX always runs while not Off**, also with no voices sounding (frozen buffers, tails and Always-on input keep playing) — skipping on silence would cut frozen loops — a silence gate could be added for Reverb only.
24. **Part-level sources for Part FX routes:** routes into Part FX P's read per-voice sources from the most recently started voice, as Part Level (M4 ruling 6).
25. **NaN guard:** a non-finite Part FX output restarts the playing engine and outputs silence for that slice (spec §9).
26. **Defaults per plugin:** instrument Part FX Off on both parts; EG13 FX Part A Granular (spec §6), Part B Off; Part FX input Part mix everywhere.
27. **CPU budget for Part FX:** the 50 % voice-chain budget and the 10 % modulation budget are unchanged; Part FX gets its own: at most 5 % of one M1 core for both parts each running its costliest Part FX setting (including rate conversion), 48 kHz, 128-sample blocks, measured in both latency modes. Planning measured ≤ 1.3 % per bare instance. If it fails, report the figures and stop — separate budgets as in M4 — the owner may merge budgets.
28. **Memory** is measured per part (Task 10) and documented; planning estimate ≈ 1.2 MB of module buffers per part (Beads 832 KiB, Clouds 180 KiB, two 64 KiB reverbs) plus converters.

## Review Focus

1. **Changing Part FX type, Quality or Mode while sounding, or automating them:** no click beyond the 10 ms fade, never NaN, output stays aligned, P values follow the engine. 4. **Changing the latency mode while active, or loading a project saved in the other mode:** the sound keeps playing in the mode it was prepared with, the reported latency always matches what is running, the new mode takes effect at the next activate, and in an AU host (no restart) nothing glitches.
